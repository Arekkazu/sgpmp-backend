## Flujo y contingencia

Dos inicios de sesión QA preceden al RUN. Dentro del RUN se consulta el catálogo I3P-1 y se elige un tipo INDIVIDUAL sin ACTIVO, prefiriendo `MODELO_ESPECIES_GRANDES`; se registra la elección. Se registran A, B, C y D APROBADAS de ese tipo con UUID RF-71 nuevos, métricas 0.91/0.93 y un ONNX mínimo. Veterinario añade notas a A y Administrador a B. A se activa y se comprueba; luego B se activa, se comprueban A/B y sus eventos; después se intentan C sin notas y D con espacios. Se cierra el RUN por DELETE y se realizan cuatro GET por ID y un listado ACTIVO sin cabecera de RUN para contrastar el rollback. Si los dos tipos INDIVIDUAL tienen ACTIVO heredada, 150 queda NO_CONCLUYENTE justificado; 151–153 siguen con `MODELO_ESPECIES_GRANDES` y la heredada se depreca dentro del sandbox.

Si activar A devuelve 5xx, 150 se rechaza y se registra su estado posterior por GET. Solo entonces se registra E APROBADA del mismo tipo, con notas del Veterinario; B se activa como primera ACTIVO y, si responde 2xx, se comprueba B ACTIVO antes de activar E. El par B→E se evalúa para 151/152 mediante GET, listado y auditorías. Si también falla B con 5xx, 151/152 se rechazan con la misma incidencia y se comprueba que A/B continúan APROBADO; cuando ambos 5xx tienen el mismo HTTP y código, una incidencia agrupa 150–152. Activar B con A ACTIVO y respuesta 5xx rechaza 151/152, comprueba A ACTIVO y B APROBADO, y consulta las auditorías de ambos. Activar C sin notas con 5xx rechaza 153; D y las lecturas finales siguen ejecutándose. Un 5xx de activación se atribuye al caso correspondiente y no vuelve técnico el RUN si cierre y rollback quedan comprobados. Tres respuestas 5xx en solicitudes consecutivas, 403 de clave y falta de respuesta mantienen el corte técnico.

El presupuesto normal exacto es **35 solicitudes**: 2 login, 1 catálogo, 1 elección/listado inicial, 4 registros, 2 notas, 2 activaciones válidas, 6 GET de versión, 5 listados, 3 auditorías, 3 solicitudes CA-13, 1 DELETE y 5 comprobaciones poscierre. La contingencia completa de A suma exactamente cinco: 1 POST de registro E, 1 PATCH de notas, 1 activación E, 1 GET de B antes de E y 1 GET poscierre de E; **máximo 40**. Si también falla B, no se intenta activar E ni el GET intermedio: **38** solicitudes. E añade un ONNX almacenado fuera del rollback. Timeout 120 s por cada login previo al RUN y por POST de registro, 30 s por el resto y duración máxima 900 s. Cada login registra duración; si no obtiene respuesta se registra `TIMEOUT` o el código de red saneado, sin reintento. Los 5xx consecutivos se cuentan por solicitudes: una lectura 2xx tras activar con 5xx reinicia el contador. En registro sin respuesta se consulta el listado, pero sin ID inequívoco el resultado sigue NO_CONCLUYENTE.

## Efectos que debe conocer la autorización externa

En contingencia de tipo ocupado, una ACTIVO heredada se depreca temporalmente y debe restaurarse. Los dos login previos podrían dejar sesión o auditoría fuera del RUN.
