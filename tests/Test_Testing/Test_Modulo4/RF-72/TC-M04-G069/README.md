# TC-M04-G069 — preparación local

Fuente: `Casos_Prueba(Mod4Agrupfinal)_actualizada.csv`, fila G069, y RF-72:4018-4019,4065,4241-4246,4301,4369-4374. 212 exige 201, luego dos 409 con el mensaje E2, original intacto y sin edición/reemplazo. 213 exige dos registros 201 independientes de A y B sobre R2. Se usan resultados de modelo INDIVIDUAL (RFC-009), R1 distinto de R2. El 409/201 es literal porque el requisito lo fija. El estado del segundo veterinario es CORRECTO para aislar la unicidad del conflicto entre estados (G072).

El router `retroalimentacion_clinica_router.py:35-75` solo define POST; no expone PUT, PATCH ni DELETE para edición, reemplazo o eliminación. Esto apoya el criterio «no se ofrece edición ni reemplazo»; los intentos de modificación por API pertenecen a G071.

En `origin/test` (`daefc3a5`), `registrar_retroalimentacion_use_case.py:100-107` detecta el duplicado antes de guardar (`:145`) y lanza `RETROALIMENTACION_DUPLICADA` con el texto E2. `src/shared/errors.py:80-88` lo convierte en 409. El esquema baseline declara `uq_retro_usuario_resultado` sobre `(id_resultado_inferencia, id_usuario_veterinario)` (`alembic/baseline/esquema_baseline.sql:39371-39375`). Si esa restricción se dispara por carrera de concurrencia, el repositorio pasa el error al traductor sin mensaje específico (`retroalimentacion_clinica_repository.py:35-54`): este devolvería `RECURSO_DUPLICADO`, HTTP 409 y mensaje genérico (`db_error_translator.py:379-384`). La prueba secuencial exige el mensaje de E2 en ambos duplicados.

El ejecutor `g069.mjs` usa un login por cuenta antes de la única invocación Newman. Cuentas por nombre: `QA_VETERINARIO_EMAIL`, `QA_VETERINARIO_B_EMAIL`, `QA_COMMON_PASSWORD`; sandbox `QA_SANDBOX_SECRET`. La sesión es única: otro login de la misma cuenta invalida el token. No se requiere Administrador: lectura de auditoría RF-73, recurso 46 R=2, está disponible para Veterinario según `auditoria_m04_router.py:14-15,56-60`. El descubrimiento consulta historial del activo 885 por 88 días con cursor y versiones de modelo. La colección ejecuta 212(a,b,c), luego 213(a,b); permite un reemplazo de R1 y uno de R2 si el primer POST recibe `RETROALIMENTACION_DUPLICADA` o `FUERA_DE_VENTANA_TEMPORAL`. Usa token A o B por solicitud, un solo reporte JSON/HTML saneado, y detiene ante 403 de clave o tres 5xx seguidos. El ejecutor lee historial y auditoría, intenta DELETE siempre tras comenzar peticiones y verifica por historial poscierre.

Presupuesto máximo exacto: **37 solicitudes** = 2 logins + 1 activo + 4 páginas de descubrimiento + 8 versiones + 7 Newman + 8 lecturas de verificación (3 páginas de historial y 1 auditoría por resultado) + 1 DELETE + 6 páginas de historial poscierre. Login 120 s; resto 30 s; RUN máximo 900 s. Preflight exige `QA_AUTORIZADO=SI` aportado por el lanzador y base TEST canónica; el ensayo admite únicamente loopback. No ejecutar contra TEST desde esta preparación.

Efectos que requieren autorización particular en la SOL: logins A/B (último acceso y auditoría de autenticación, primer acceso real de B); lecturas de activo, historial, versiones y auditoría; tres retroalimentaciones previstas (A en R1, A y B en R2) y auditoría correspondiente, revertidas por DELETE; dos rechazos 409 sin persistencia; reemplazos condicionales de precondición; lecturas poscierre con posible `HISTORIAL_CONSULTADO` fuera del sandbox. Sin correos ni archivos; semilla sin modificación. Un 5xx aislado rechaza solo su caso si la precondición está montada; tres 5xx o 403 de clave bloquean técnicamente. Sin respuesta exige conciliación. Nunca se declara RECHAZADO sin evidencia de TEST.
