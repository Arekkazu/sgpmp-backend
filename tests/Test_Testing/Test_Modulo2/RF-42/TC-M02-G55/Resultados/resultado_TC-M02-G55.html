Collection Description
TC-M02-G55 (RF-42, CU08 Gestionar eventos reproductivos), equivalente a TC-M02-101 y TC-M02-102. ENDPOINT REAL BAJO PRUEBA: POST /activos-biologicos/{id_activo}/eventos/reproductivo (RegistrarEventoReproductivoUseCase, src/biological_assets/application/use_cases/gestion/registrar_evento_reproductivo_use_case.py). Sub-caso 1 (TC-M02-101): un activo POBLACIONAL (lote) solo puede registrar eventos reproductivos de categoria 'nacimiento'; cualquier otra categoria (aqui 'parto') debe rechazarse con HTTP 422 y code=EVENTO_NO_PERMITIDO_LOTE ('El tipo de evento no esta permitido para el tipo de activo'). HALLAZGO CRITICO (confirmado en vivo el 2026-09-08/09, mismo patron de bug que TC-M02-G53, backend no resuelto): la validacion Python de esta regla (linea 56 del use case) compara `activo.tipo == 'LOTE'`, pero el valor real que toma `activo.tipo` para un activo poblacional es 'POBLACIONAL' (unico valor aceptado por el enum modulo2.enum_activo_biologico_tipo y por RegistrarActivoBiologicoDTO junto con 'INDIVIDUAL') -- 'LOTE' nunca es un valor posible en este campo. Por lo tanto esta validacion de Python es CODIGO MUERTO: nunca se dispara para ningun activo real, y la ejecucion sigue de largo hasta el INSERT en modulo2.eventos_reproductivos. A nivel de base de datos SI existe la validacion correcta -- el trigger trg_fn_evento_reproductivo_secuencia (esquema_baseline.sql linea ~5874-5878) hace `IF v_tipo_activo = 'POBLACIONAL' AND NEW.categoria NOT IN ('nacimiento') THEN RAISE EXCEPTION 'TYPE_RESTRICTION...' USING ERRCODE = 'P0220'` -- pero ese ERRCODE personalizado (P0220) no esta mapeado por raise_from_db_error() (src/shared/db_error_translator.py solo traduce IntegrityError/DataError/OperationalError), asi que la excepcion cae al catch-all generico: HTTP 500 ERROR_INTERNO ('Error inesperado en base de datos') en vez del 422 EVENTO_NO_PERMITIDO_LOTE que espera el RF. Mismo mecanismo raiz que el bug ya documentado en TC-M02-G53 -- refuerza que el gap esta en el traductor de errores de BD, no es un caso aislado del primer evento reproductivo. Sub-caso 2 (TC-M02-102): registrar un evento tipo 'servicio' con `id_padre` apuntando a un activo que NO existe debe rechazarse con HTTP 404 y code=ACTIVO_RELACIONADO_NO_ENCONTRADO. Esta validacion (lineas 69-79 del use case) es enteramente Python, antes de cualquier INSERT -- no deberia verse afectada por el bug anterior. Se espera que este sub-caso SI pase. Esta coleccion se deja intencionalmente afirmando el comportamiento CORRECTO esperado por el RF (422 en sub-caso 1) en vez de ajustarse al 500 actual: un Newman en rojo en el sub-caso 1 es la evidencia documentada de este defecto, mismo criterio aplicado en TC-M09-G64 y TC-M02-G53. La coleccion es autocontenida: registra su propio lote (activo POBLACIONAL, especie Tilapia id=10, cantidad_inicial=50) sobre un area productiva activa ya existente en TEST (finca_id=1, id_infraestructura=3).
