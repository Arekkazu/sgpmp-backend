6. Escenario POBLACIONAL ACTIVO con ciclo abierto y cantidad_actual = 0 (TC-M05-041):
   - Veredicto: BLOQUEADO POR REGLA DE NEGOCIO M02 / VIABLE ÚNICAMENTE MEDIANTE SEED DBA.
   - Justificación técnica: En el modelo de dominio de Módulo 2, un lote POBLACIONAL no puede crearse con cantidad <= 0 (RegistrarActivoBiologicoDTO:69 rechaza con 400). Si se aplica baja total (RF-36), el use case RegistrarEventoBajaUseCase:168 fuerza requiere_cierre = True, pasando automáticamente el lote a BAJA (6) o CERRADO (5). En ese estado, el validador de RF-76 rechaza en el Paso 2 (ACTIVO_ESTADO_INVALIDO 422) antes de alcanzar la validación de cantidad_actual en el Paso 8 (POBLACIONAL_SIN_CANTIDAD). Por API es estructuralmente imposible tener un lote en estado ACTIVO con cantidad_actual = 0 y ciclo abierto simultáneamente.

7. Escenario POBLACIONAL ACTIVO con ciclo abierto y cantidad_actual = NULL (TC-M05-041):
   - Veredicto: VIABLE PROVOCANDO ESTADO EN SANDBOX (Activo 462).
   - Justificación técnica: El Activo 462 en TEST es POBLACIONAL en estado ACTIVO (1) y no posee detalle poblacional registrado (detalle_poblacional = None / cantidad_actual = NULL). Dentro de la corrida sandbox se abre una fase con un ciclo compatible (POST /activos-biologicos/462/fases -> 201 Created), logrando exactamente la precondición de ciclo abierto. Al invocar POST /suministros/medicamentos responde determinísticamente HTTP 422 POBLACIONAL_SIN_CANTIDAD. Tras el teardown con rollback, la fase se revierte y el activo queda intacto.

8. Escenario AISLADO (Diagnóstico opcional):
   - Veredicto: VIABLE con activo preexistente en TEST (Activo 812).
   - Comportamiento observado: Rechazo HTTP 422 con error_code="ACTIVO_ESTADO_INVALIDO".

INFERENCIAS (Deducidas de la lectura de código fuente):
1. El código de RegistrarMedicamentoUseCase evalúa en orden estricto: existencia -> estado -> ciclo abierto -> fecha futura -> fecha inicio ciclo -> vía -> evento sanitario -> cantidad poblacional -> duplicados.
2. Por lo tanto, un activo en BAJA o CERRADO con cantidad_actual = 0 jamás llegará a evaluar la cantidad poblacional en el Paso 8, porque el Paso 2 corta la ejecución primero.
3. El documento de análisis CU-03 existe en el repositorio en anotaciones/modulo_5/cu03_verificacion_rf76.md y confirma la trazabilidad de los flujos FA-01 a FA-16 y errores E1 a E13.

HALLAZGOS FUERA DE ALCANCE PARA ANÁLISIS:
1. Conflicto documental en CU03 (FA-10 vs E10): FA-10 indica que si falla RF-44 el medicamento debe quedar persistido y registrar incidente en auditoría, mientras que E10 exige rollback atómico completo (HTTP 500). El backend implementa E10 (rollback atómico), lo cual es conforme con el RNF de fiabilidad de RF-76.
2. Inconsistencia entre RF-76 y M02 sobre lotes con 0 individuos: RF-76 menciona "verificar cantidad poblacional > 0", pero en M02 cualquier lote cuya cantidad llegue a 0 mediante baja queda automáticamente cerrado y en estado BAJA.
