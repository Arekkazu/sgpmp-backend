3. HIPOTESIS Y CONTRASTACION
--------------------------------------------------------------------------------
- Hipótesis 1: El caso de uso captura cualquier error genérico y despacha auditoría pero el rollback cancela la inserción.
  [DESCARTADA]: En `registrar_suministro_directo_use_case.py:271-274`, el bloque `except AppError` solo hace `self.db.rollback()` y `raise`. No existe ninguna llamada a `self.auditoria_port.registrar()` dentro de dicho bloque.
- Hipótesis 2: El método `_registrar_fallo` está reservado exclusivamente para fallos transitorios de infraestructura.
  [CONFIRMADA]: `_registrar_fallo` solo se ejecuta cuando se captura `_ERRORES_REINTENTABLES` (fallos de conexión a BD o timeout de infraestructura). Las excepciones controladas de validación de negocio (`BusinessRuleError`, `ValidationError`) escapan inmediatamente sin auditarse.

4. CAUSA MAS PROBABLE, CLASIFICACION Y CAUSA RAIZ COMPARTIDA
--------------------------------------------------------------------------------
- Causa Más Probable: Omisión en el diseño de la capa de aplicación: el use case no contempla auditar los rechazos de reglas de negocio cuando una operación de suministro es abortada por precondiciones inválidas.
- Clasificación: Defecto de Producto.
- Causa Raíz Compartida: Falta de un mecanismo transversal desacoplado para auditar rechazos controlados sin que el rollback de la transacción principal interfiera (compartida con G38-C02 y G39-B02).

5. POSIBLE SOLUCION (LENGUAJE DE DESARROLLO)
--------------------------------------------------------------------------------
- En `registrar_suministro_directo_use_case.py`:
  En el bloque `except (BusinessRuleError, ValidationError) as exc:`, antes de relanzar la excepción:
  1. Abrir una sesión independiente o ejecutar `auditoria_port.registrar()` con `autocommit` aislado (o vía background task).
  2. Registrar `EventoAuditoriaSuministro` con:
     * `tipo_operacion="REGISTRO_FALLIDO"`
     * `resultado="RECHAZADO"` o `"FALLIDO"`
     * `detalle_causa=exc.message`
     * `id_activo_biologico=dto.id_activo_biologico`
     * `id_usuario=usuario_actual.id_usuario`
  3. Ejecutar rollback de la transacción de negocio principal y relanzar la excepción HTTP para mantener el código 409/422 al cliente.

6. CRITERIO DE RE-PRUEBA
--------------------------------------------------------------------------------
- Enviar POST `/suministros/costeo-directo` con datos que incumplan reglas de negocio (ej. activo con ciclo cerrado -> HTTP 409).
- Consultar GET `/suministros/auditoria?id_activo_biologico=<id>&tipo_operacion=REGISTRO_FALLIDO`.
- Verificar que retorne HTTP 200 con al menos 1 evento que contenga `resultado="FALLIDO"` (o `"RECHAZADO"`) y `detalle_causa` con el mensaje de error.

BORRADOR DE INCIDENTE FORMAL
================================================================================
INC-ID: INC-M05-G37-01
Título: Omisión de registro de auditoría ante rechazos por reglas de negocio en suministro directo
Módulo: Módulo 5 (Suministros y Alimentación)
Categoría: ESTADO
Severidad: Severo
Casos Afectados: TC-M05-026 (Plano) / TC-M05-002 (Agrupado)
Criterio de Aceptación: RF-80 CA-11 / CU06 Flujo Alterno
Descripción:
Al invocar POST /suministros/costeo-directo con parámetros que violan reglas de negocio (ej. activo con ciclo cerrado, código CICLO_NO_ACTIVO, HTTP 409), el backend retorna correctamente el error al cliente pero omite por completo la persistencia del evento fallido en modulo5.auditorias_suministros.
Pasos para Reproducir:
1. Crear un activo poblacional y cerrar su ciclo productivo.
2. Enviar POST /suministros/costeo-directo hacia dicho activo.
3. Observar respuesta HTTP 409 Conflict.
4. Consultar SELECT count(*) FROM modulo5.auditorias_suministros WHERE tipo_operacion = 'REGISTRO_FALLIDO'.
Resultado Esperado: count >= 1.
Resultado Obtenido: count = 0.
Impacto: Pérdida total de trazabilidad forense ante operaciones rechazadas, impidiendo auditar intentos de registro sobre activos inactivos.
