ERROR 2: G39-B02 (TC-M05-093 / 029) - 405 sin Evento de Seguridad en Bitacora
--------------------------------------------------------------------------------
1. Que se observo exactamente (Hecho observado):
   - Peticiones de prueba: PUT, PATCH, DELETE sobre /suministros/auditoria y /suministros/auditoria/{id}.
   - Respuesta HTTP: 405 Method Not Allowed con cuerpo {"detail": "Method Not Allowed"}.
   - Fila evaluada y hash_integridad: Permanecieron intactos (inmutabilidad preservada a nivel HTTP).
   - Consulta de seguridad: SELECT count(*) FROM modulo5.auditorias_suministros WHERE resultado = 'RECHAZADO';
   - Resultado: 0 eventos registrados. Tampoco se registraron eventos en modulo1.eventos.
2. Ruta de codigo completa (Inferencia contrastada):
   - Capa de Enrutamiento: Starlette Routing Engine (starlette.routing.Router.matches).
   - Al encontrar coincidencia de ruta pero verbo no registrado, Starlette lanza:
     starlette.exceptions.HTTPException(status_code=405, detail="Method Not Allowed")
   - Handlers globales: src/shared/error_handlers.py:register_error_handlers:386-399.
     No existe un exception handler registrado para HTTPException ni para codigo 405.
   - La peticion es abortada por el framework antes de que se instancie ningun router, use case ni sesion de BD.
3. Hipotesis y contrastacion:
   - H1: Un middleware de auditoria intercepta y audita el 405 pero la BD falla. DESCARTADA: No existe tal middleware
     en src/shared/middlewares.py.
   - H2: El 405 lo emite Starlette de forma nativa sin pasar por el codigo de la aplicacion. CONFIRMADA: Starlette
     resuelve el ruteo a nivel de framework ASGI antes de invocar las dependencias de FastAPI.
4. Causa mas probable, clasificacion y causa raiz compartida:
   - Causa Mas Probable: Inexistencia de un manejador de excepciones para HTTP 405 que capture y audite intentos
     de mutacion en endpoints protegidos.
   - Clasificacion: Defecto de Producto / Brecha de Auditoria de Seguridad.
   - Causa Raiz Compartida: Ausencia de auditoria transversal de seguridad para eventos HTTP 403 y 405
     (compartida con G38-C02).
5. Posible solucion (Desarrollo):
   - En src/shared/error_handlers.py: Registrar un handler para HTTPException de Starlette:
     @app.exception_handler(HTTPException)
     async def http_exception_handler(request: Request, exc: HTTPException):
         if exc.status_code == 405 and request.url.path.startswith("/suministros/auditoria"):
             _auditar_intento_mutacion_seguridad(request)
         return JSONResponse(status_code=exc.status_code, content={"error_code": "METODO_NO_PERMITIDO", "message": exc.detail})
6. Criterio de re-prueba:
   - Enviar PUT /suministros/auditoria y verificar que la respuesta sea 405 y se inserte 1 evento en la bitacora
     con resultado='RECHAZADO' y tipo_operacion='INTENTO_MODIFICACION_NO_PERMITIDO'.

ASPECTO ADICIONAL: G39-B03 (TC-M05-093 / 029) - Formula de Hash y Campos Excluidos
--------------------------------------------------------------------------------
1. Que se observo exactamente (Hecho observado):
   - Definicion de la funcion en catalogo pg_proc:
     NEW.hash_integridad := encode(digest((
       SELECT string_agg(format('%I=%L', key, value), ' & ' ORDER BY key)
       FROM jsonb_each_text(to_jsonb(NEW) - 'hash_integridad' - 'creado_en' - 'id_registro_suministro')
     ), 'sha256'), 'hex');
   - Consulta a columnas de modulo5.auditorias_suministros:
     Las columnas 'creado_en' e 'id_registro_suministro' NO existen en la tabla.
2. Analisis de impacto:
   - En PostgreSQL, restar claves inexistentes a un objeto JSONB (to_jsonb(NEW) - 'creado_en') es una operacion inocua (no-op).
   - Por tanto, la funcion incluye TODOS los campos reales existentes en la fila ordenados alfabeticamente.
   - La inclusion en la definicion obedece a copia de plantilla de trigger de otra tabla (ej. registro_suministro).
   - Verificacion de integridad: Se comprobo que recalcular el SHA-256 en Python sobre los campos reales coincide al 100%
     con el valor almacenado en BD.
   - Inexistencia de verificacion periodica: No existe en catalogo de BD ni en el backend ningun cron, job ni funcion
     programada para recalcular periodicamente los hashes (CA-9, RNF-06).
   - Clasificacion: Deuda tecnica menor en DDL (inocua para el calculo del hash actual).
