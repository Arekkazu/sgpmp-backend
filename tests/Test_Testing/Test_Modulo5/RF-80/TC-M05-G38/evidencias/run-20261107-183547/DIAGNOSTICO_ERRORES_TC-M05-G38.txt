SUB-CASO 1: G38-B01 (TC-M05-044.1 / 032) - Filtro fecha_desde > fecha_hasta
--------------------------------------------------------------------------------
1. Que se observo exactamente (Hecho observado):
   - Peticion: GET /suministros/auditoria?fecha_desde=2026-11-10T00:00:00Z&fecha_hasta=2026-11-01T00:00:00Z
   - Respuesta HTTP: 200 OK con cuerpo {"total": 0, "pagina": 1, "registros_por_pagina": 50, "items": []}.
   - Especificacion: Exige HTTP 4xx con mensaje explicativo indicando que fecha_desde no puede ser mayor que fecha_hasta.
2. Ruta de codigo completa (Inferencia contrastada):
   - Router: src/supplies/infrastructure/routers/auditoria_suministros_router.py:55-87
   - DTO / Value Object: src/supplies/domain/repositories/auditoria_suministro_read_port.py:FiltrosAuditoriaSuministro
   - Caso de Uso: src/supplies/application/use_cases/auditoria/consultar_auditoria_suministros_use_case.py:21-24
   - Repositorio Read: src/supplies/infrastructure/repositories/auditoria_suministro_read_repository.py:63-66
   - Motor SQL: Cláusulas WHERE fecha_evento >= fecha_desde AND fecha_evento <= fecha_hasta producen conjunto vacio.
3. Hipotesis y contrastacion:
   - H1: El router valida pero un middleware lo transforma a 200. DESCARTADA: No existe codigo de validacion
     de coherencia temporal entre fecha_desde y fecha_hasta en el router ni en Pydantic.
   - H2: La logica de base de datos maneja la condicion AND sin error. CONFIRMADA: En SQL un rango invertido
     evalua a falso para todas las filas y retorna 0 registros sin excepcion.
4. Causa mas probable, clasificacion y causa raiz compartida:
   - Causa Mas Probable: Omision de validacion cruzada de parametros temporales en el endpoint.
   - Clasificacion: Defecto de Producto.
   - Causa Raiz Compartida: Falta de validacion temporal coherente en query parameters de routers de consulta.
5. Posible solucion (Desarrollo):
   - En auditoria_suministros_router.py (o dependencia de validacion):
     if fecha_desde and fecha_hasta and fecha_desde > fecha_hasta:
         raise ValidationError(code="RANGO_FECHAS_INVALIDO", message="fecha_desde no puede ser posterior a fecha_hasta")
6. Criterio de re-prueba:
   - Invocar GET /suministros/auditoria?fecha_desde=2026-12-01&fecha_hasta=2026-11-01 y verificar HTTP 400
     con error_code="RANGO_FECHAS_INVALIDO".

1. Que se observo exactamente (Hecho observado):

   - Respuesta HTTP: 403 Forbidden con {"error_code": "ACCESO_DENEGADO"}.
   - Consulta a BD: SELECT count(*) FROM modulo5.auditorias_suministros WHERE resultado = 'RECHAZADO';
   - Resultado: 0 eventos registrados.
2. Ruta de codigo completa (Inferencia contrastada):

   - RBAC: src/shared/rbac.py:require_permission:104-115
   - Comprobacion: src/shared/rbac.py:_exigir_permiso:155-162 -> raise AuthorizationError(...)
   - Handler: src/shared/error_handlers.py:app_error_handler:76-100 (retorna 403 sin persistir en BD).
3. Hipotesis y contrastacion:
   - H1: El fallo 403 se persiste en modulo1.eventos. DESCARTADA: rbac.py no interactua con el modulo de eventos
     ni inyecta ningun repositorio de seguridad.
   - H2: rbac.py es puramente defensivo y solo lanza la excepcion. CONFIRMADA: rbac.py se limita a verificar
     el permiso en modulo1.permisos y lanzar AuthorizationError sin disparar efectos secundarios.
4. Causa mas probable, clasificacion y causa raiz compartida:
   - Causa Mas Probable: Desacoplamiento de la compuerta RBAC sin enlace a la bitacora de auditoria de seguridad.

     (compartida con G39-B02).
5. Posible solucion (Desarrollo):
   - En src/shared/rbac.py o en un middleware de seguridad: al denegar acceso, invocar un servicio
     asincrono de auditoria de seguridad que persista el evento denegado (usuario, rol, recurso, endpoint, ip).
6. Criterio de re-prueba:
   - Intentar acceder con rol no autorizado (403) y verificar que se genere 1 evento con resultado 'RECHAZADO'.
