## Dependencias de datos y escenario

`GET /finanzas/activos` y `GET /finanzas/periodos` aportan candidatos y períodos; luego se consulta una sola vez `GET /finanzas/precios?id_especie=<id>` por especie bovina candidata. Se seleccionan cuatro bovinos individuales reconocidos, distintos, con valor razonable positivo, inicialmente ACTIVO, precio `PESO_KG` vigente y período destino ABIERTO del titular, solo si el periodo del titular que contiene hoy esta ABIERTO; CERRADO o EN_CIERRE descartan el activo. `GET /finanzas/activos/{id}` aporta el titular tributario y el último cálculo previo (magnitud, precio y valor neto); `GET /activos-biologicos/{id}/ficha-integral` aporta peso actual en kg. El Contador QA hace las solicitudes M06 y el Administrador QA las M02, que requieren permiso `activos_biologicos` de creación (`activo_biologico_router.py:1216–1220`). Para TC-M06-002 se registra primero el pesaje en ACTIVO, luego se hace `PATCH /activos-biologicos/{id}/estado` a EN_TRATAMIENTO y finalmente se procesa M06. RF-40 de M02 solo permite eventos de crecimiento en ACTIVO (`Especificacion-Requerimientos-Modulo2.md:2194`, `registrar_evento_crecimiento_use_case.py:84–93`). El procesador M06 no filtra EN_TRATAMIENTO (`procesar_eventos_m02_use_case.py:84–111`); el proceso periódico usa `sesion_sistema` separada y no puede leer el evento sin confirmar del sandbox (`main.py:599–630`). Si falla un requisito bloqueante del preflight, los cuatro casos quedan NO_CONCLUYENTE sin escrituras; DELETE se envia siempre. Durante la prueba, cada subcaso independiente conserva su propio resultado. El ejecutor no crea activos, reconocimientos, períodos, matriz RF-109, parámetros M09 ni titular RF-19. La cadena imprescindible es RF-19 → activo M02 con especie, fase y peso admitido por M09 → precio vigente RF-89 + costos de venta RF-84 → reconocimiento RF-82 CONFIRMADO y matriz RF-109 → período RF-87 ABIERTO → evento M02 → medición RF-83 → variación RF-86. M02 valida fase, rango de peso y configuración de la especie (`registrar_evento_crecimiento_use_case.py:27–33, 125–144`; router `activo_biologico_router.py:1196–1216`). Los **nombres** `QA_CONTADOR_EMAIL`, `QA_CONTADOR_PASSWORD`, `QA_ADMIN_EMAIL` y `QA_ADMIN_PASSWORD` están presentes en `.env.qa`; no se leyó ningún valor en esta preparación. La existencia de cuentas usables y sus permisos solo podrá comprobarse en un RUN autorizado.

Se usa la misma especie y fuente `MERCADO_ACTIVO` para los precios: RF-89 prioriza esa fuente y el registro más reciente (`precios.py:44–52`). Primero se hacen los dos subcasos sin registrar nuevo precio. Para TC-M06-001 y TC-M06-002 se prefieren activos cuyo cálculo previo ya usó el precio vigente. Si difiere en cualquiera de ellos, se registra y procesa un evento M02 con el mismo peso para actualizar la base; se confirma por lectura pública que el cálculo nuevo usa el precio vigente y se fija después la línea base de variaciones. El posible PM de cada rebase queda fuera del oráculo del evento evaluado en TC-M06-001 o TC-M06-002. El pesaje que baja el peso se registra en ACTIVO, luego se cambia a EN_TRATAMIENTO y se procesa. Se exige una sola PERDIDA_TRANSFORMACION_BIOLOGICA y ningún PM para ese pesaje. Después se registra un precio 5 % menor para TC-M06-003 y uno 5 % mayor para TC-M06-004. Los cuatro activos son independientes. El procesamiento explícito hace visible el trabajo en la sesión aislada, sin introducir componentes contables manualmente.

Se fija la línea base antes de cada evento evaluado. Por caso se conservan IDs, tipos, montos, período, VR, fecha, estado inicial `VERIFICACION_PENDIENTE`, medición RF-83 y valores esperados. Después de comprobar esos oráculos en los cuatro casos se hace un solo POST `/finanzas/periodos/{id}/trazabilidad` por período destino, como Contador y dentro del sandbox. Entonces se consultan las cadenas de las líneas y sus `eslabones.ids`: TB debe tener `id_evento` del evento M02; PM debe tener `id_precio_mercado` del precio RF-89. El listado de variaciones omite esos IDs (`valoracion_repository.py:307–319`); la cadena RF-91 los expone tras registrar la verificación (`trazabilidad_repository.py:91–117`). Se guardan HTTP, código, cuerpo saneado e IDs observados en `resultado.json`. POST 5xx o cadena sin los IDs exigidos deja RECHAZADO el origen con una incidencia de producto para Desarrollo, sin inferir causa raíz. No se evalúa unicidad de `fecha_registro`, pues una transacción del sandbox comparte `now()`.

## Ejecución prevista y presupuesto

El lanzador externo es el único que puede invocar `--operacion evaluar|reintentar|reevaluar --version N --intento N --run-id RUN-G32-VN-AAAAMMDD-HHMMSS --autorizacion REFERENCIA --contexto RUTA`. Debe crear antes el RUN canónico y aportar `QA_AUTORIZADO=SI`; el ejecutor carga `.env.qa` mediante `leerEnv`. `--capacidades` y `--comprobar` son locales. Los logins quedan fuera del RUN. Las solicitudes dentro del RUN llevan `X-Test-Run-Id` y `X-Sandbox-Secret` y comprueban el eco. El DELETE de cierre lleva `X-Sandbox-Secret` sin depender de `runId`; las lecturas públicas poscierre no llevan cabeceras del RUN. Un POST sin respuesta no se repite. Se corta ante 403 o tres 5xx principales consecutivos. Los timeouts son 120 s para login y POST, 30 s para el resto. Límite: 150 solicitudes y 2400 s; desglose máximo reservado: 2 logins, 1 cambio de estado, 6 eventos M02, 2 precios, 6 disparos, hasta 2 verificaciones RF-91 (escenario y periodo 8), 130 lecturas y 1 DELETE. Los eventos y procesamientos adicionales de TC-M06-001 y TC-M06-002 solo ocurren si hace falta el rebase. El cambio de estado sigue al pesaje evaluado.

La colección Newman hace cuatro lecturas públicas suplementarias mediante su reporter JSON y se invoca con `process.execPath`. El hijo fija `reporter.json.export` (equivalente a `--reporter-json-export`) en un directorio de `os.tmpdir()` y lo elimina al finalizar; nunca usa la ruta implícita `./newman`. `resultado.json` conserva las comprobaciones semánticas del ejecutor. El resumen JSON saneado y el HTML propio se escriben solo en `Resultados/RUN-…/newman/` o `EvaluacionV*/Resultados/RUN-…/newman/` durante una ejecución real. El ensayo `node pruebas/g32_ensayo.mjs` usa exclusivamente loopback, comprueba que no aparezcan archivos nuevos en el grupo y no crea RUN ni informes.

**Efecto fuera de sandbox confirmado en código y documentado para la SOL de V2 y sujeto a la autorización del RUN en curso:** cada precio vigente no PRODUCTO llama a `notificador.a_contadores` después del commit (`registrar_precio_use_case.py:89–96`); el adaptador usa una sesión propia, crea un evento M01 y una notificación interna por cada Contador destinatario y hace commit propio (`notificacion_financiera_m01_adapter.py:1–5, 42–70`). Los avisos quedan en la bandeja interna con referencia a precios que el sandbox revierte. La cantidad de Contadores destinatarios no se presupone. Se consulta solo la bandeja pública del Contador QA antes y después, y se informa el número de avisos nuevos reconocibles; si la lectura no permite contarlos, se declara `NO_VERIFICABLE`. Esta observación no condiciona oficialidad ni veredictos. El login fuera del RUN puede dejar sesión o auditoría. Las lecturas M02 pueden crear bitácora de consulta. No se ejecutó TEST en esta fase.

Si DELETE falla, se registra HTTP y cuerpo saneado, el rollback queda sin verificar y no se hacen lecturas poscierre; el informe indica el cierre por inactividad pendiente y si la bitácora no registra intentos de escritura. Un GET de precios filtrado con 5xx bloquea los subcasos dependientes y conserva el cuerpo saneado como impedimento observado en RF-89, con primera atención de Desarrollo y causa raíz no determinada. `rollback.verificado` exige DELETE 200 y lecturas públicas poscierre que no muestren los IDs creados de precios RF-89, eventos M02 y variaciones RF-86; si se preparó EN_TRATAMIENTO, comprueba además el estado anterior del activo. Un precio sin ID conciliable deja el rollback sin verificar. La notificación M01 aceptada queda en `efectos_persistentes_declarados` y no forma parte de esa comprobación. Solo con rollback verificado, cuatro casos concluyentes y Newman válido se marca `oficial=true`; el ensayo local usa `OFICIAL_LOCAL` sin producir RUN.
