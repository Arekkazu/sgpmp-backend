# TC-M03-G96 — TC-M03-187

## Oráculo vigente

La fila vigente de `Casos_Prueba(Modulo3 Agrupado).csv` exige literalmente «El estado de conectividad presentado por el monitoreo utiliza exclusivamente uno de los cinco estados definidos por RF-60 (ACTIVO, SIN_SEÑAL, BUFFER_ACTIVO, INACTIVO o EN_MANTENIMIENTO) y coincide con el estado del dispositivo; no se exponen valores diferentes al catálogo establecido.»

Decisión del líder de análisis de requerimientos del 2026-10-31 (`estado/DECISION-G96-CATALOGO.md` en el orquestador, según ORD-G96-006): rige RF-60 con **ACTIVO, SIN_SEÑAL, BUFFER_ACTIVO, INACTIVO y EN_MANTENIMIENTO**. Los tres valores de RF-58 son una inconsistencia de la ficha; no hay correspondencia que aplicar. ONLINE/OFFLINE queda solo para RF-54. Para TC-M03-187 se esperan los cinco estados. DESCONOCIDO sigue en revisión y se registra como observación sin rechazar por sí solo. El color de presentación corresponde a RF-60 fase 7, pero el caso original y el contrato de capacidades son solo API.

`API-187-01` comprueba que cada sensor en el dashboard filtrado tenga un valor del catálogo. ONLINE, OFFLINE, null, campo ausente u otro valor fuera del catálogo causa RECHAZADO con evidencia de TEST. `API-187-02` recorre los dispositivos de cada estado en `GET /iot/dispositivos?estado=<E>` como Administrador, identifica los visibles al Productor mediante su listado y prueba áreas con canarios `por_pagina=1`. Recorre páginas canario dentro del presupuesto para exigir un sensor del propio dispositivo; si no aparece, prueba las demás candidatas. Excluye áreas con GRIS no desactualizado o sin umbral antes de Newman; prioriza Productor y usa Administrador si falta candidato visible. Coteja por `id_dispositivo_iot` todos los dispositivos de las áreas consultadas y registra el rol del dashboard. Una diferencia, incluidos BUFFER_ACTIVO/EN_MANTENIMIENTO mostrados como SIN_SEÑAL, causa RECHAZADO y se deriva inicialmente a Desarrollo contra RF-60 postcondición 3. Si no existe dispositivo o sensor visible para un estado, esa cobertura es NO_CONCLUYENTE: no se crean datos. SIN_SEÑAL sin dispositivos no puede construirse sin escrituras; el responsable QA decide el veredicto global ante cobertura parcial. La discrepancia del código local es `DEFECTO_FUNCIONAL_CANDIDATO` hasta evidencia pública de TEST.

Lectura local para esta preparación: `alembic/versions/8a8f1dae36f1_rfc020_conectividad_dashboard_estado_dispositivo.py` (RFC-020 #794, 2026-10-29) describe que las transiciones del dispositivo, incluida EN_MANTENIMIENTO, se copian a la caché de sus sensores; la ingesta toma el estado del dispositivo o DESCONOCIDO si falta. También se consultaron `src/telemetry/infrastructure/schema/monitoreo_schema.py` y `src/telemetry/infrastructure/repositories/monitoreo_repository.py` para los campos del canario. No se acredita el despliegue en TEST con esta lectura.
