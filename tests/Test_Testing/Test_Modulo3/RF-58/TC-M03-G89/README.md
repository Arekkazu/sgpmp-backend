## Adaptación vigente ORD-G89-010

La vía pública elegida es `POST /iot/alertas` con `origen_evento=EDGE`, sobre el sensor 552 y con telemetría real vinculada. Para `TEMPERATURA_AMBIENTAL`, RF-57 define CRITICO si el valor supera 36 °C, MODERADO si supera 33 °C y LEVE si supera 30 °C; se usan 37, 34 y 31 °C, respectivamente (`src/telemetry/domain/entities/reglas_base_rf57.py:49-52`). El caso de uso de `origin/test` evalúa valor y correlación antes de crear la alerta (`src/telemetry/application/use_cases/alertas/generar_alerta_use_case.py:161-175`); además exige la condición mínima de ESTRES_TERMICO (`:429-466`). Se envía `correlacion_variables={"HUMEDAD_RELATIVA":40}` en los tres eventos, que produce THI 85.20, 77.97 y 81.58, respectivamente (`reglas_base_rf57.py:66-75,92-112,131-148`). Se consultaron los DTO, reglas y caso de uso de `origin/test` mediante Git de solo lectura. La humedad 40 es un dato sintético explícito del evento QA, no una lectura acreditada de un sensor de TEST; no se crea otro recurso. E14 no consulta la lectura compañera al estar presente la correlación (`generar_alerta_use_case.py:377-387`, `reglas_base_rf57.py:175-181`).

Cada evento se origina en una ingesta de su mismo valor, usa ese `id_telemetria` y `timestamp_captura`, y después se ingiere 25 °C. El GET `/iot/alertas/{id}` acredita `ACTIVA`, severidad y sensor 552; el GET del dashboard acredita que la última lectura corresponde a la ingesta normal, cae en el rango obtenido de M09 y tiene el color exigido por RF-58. La vía IA se descartó porque `PREDICCION_PATOLOGIA` requeriría una inferencia real y una probabilidad que cumpla el mínimo (`generar_alerta_use_case.py:177-186`); inventar esos datos no sería una semilla válida. El DTO externo exige trazabilidad a un evento o telemetría (`procesar_evento_alerta_dto.py:17-43,133-147`), y el router permite el POST con token de broker (`alerta_router.py:112-154`). Una ingesta desviada podría generar una alerta por el worker RF-17→RF-57; un duplicado inesperado queda como ERROR_QA y se conserva su respuesta POST. No se asume su resultado sin TEST.

Las tres respuestas POST se guardan saneadas en `api/POST-ALERTA-<severidad>.json`, incluyendo HTTP, `es_duplicado`, `id_alerta`, `motivo_descarte`, `severidad` y, ante error, el cuerpo, `error_code`, `message` y `fields`. Toda escritura no 2xx conserva además el cuerpo saneado en `api/ERROR-*.json`, enlazado desde `resultado.json` y visible en la bitácora del informe. Un 422 en el alta es un problema técnico del escenario, sin veredicto funcional. Un 201 sin ID deja el caso sin veredicto y muestra el motivo en `resultado.json` y el informe V2; una severidad distinta se clasifica ERROR_QA. Las alertas creadas se acreditan por GET y se registran para verificar rollback. Los oráculos y los IDs de comprobación permanecen intactos. Esta preparación no creó RUN ni consultó TEST.
