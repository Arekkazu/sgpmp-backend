Collection: TC-M09-G62 - Validaciones de integridad al asociar sensores a areas productivas
Collection Description
TC-M09-G62 (RF-22, CU-05 Gestionar Dispositivos IoT) agrupa 5 escenarios de validacion/rechazo sobre POST /configuracion/sensores/{id_sensor}/asociar (AsociarSensorAreaUseCase), equivalentes a TC-M09-118, 119, 120, 121 y 123: 1. Existencia de sensor y dispositivo antes de asociar. 2. Solo se puede asociar un sensor con el dispositivo al que realmente pertenece. 3. El area debe existir y estar activa (inexistente / inactiva). 4. No se permite una asociacion duplicada ya vigente (mismo sensor + misma area). 5. Un sensor no puede tener mas de una asociacion activa simultanea (reasignar a otra area exige confirmar=true). Contrato real verificado en el codigo (AsociarSensorAreaUseCase.execute(), src/configuration/application/use_cases/sensores/asociar_sensor_area_use_case.py): - Sensor inexistente -> NotFoundError, HTTP 404, error_code SENSOR_NO_ENCONTRADO. - IMPORTANTE (hallazgo de esta prueba): el use case NO recibe un repositorio de dispositivos IoT y por lo tanto NO valida por separado que id_dispositivo_iot exista - solo compara sensor.id_dispositivo_iot != dto.id_dispositivo_iot. Un id_dispositivo_iot inventado (que no coincide con el dispositivo real del sensor) cae en el MISMO error que un dispositivo real pero equivocado: BusinessRuleError, HTTP 422, error_code SENSOR_DISPOSITIVO_INVALIDO. No existe un error distinto tipo 'DISPOSITIVO_NO_ENCONTRADO' en este endpoint. El enunciado 'debe validar la existencia del dispositivo' se cumple entonces de forma indirecta, a traves de la relacion sensor-dispositivo, no con una busqueda propia del dispositivo. - Area inexistente -> NotFoundError, HTTP 404, error_code AREA_NO_ENCONTRADA. - Area inactiva -> BusinessRuleError, HTTP 422, error_code AREA_NO_DISPONIBLE. - Asociacion duplicada (mismo sensor + misma area ya vigente) -> ConflictError, HTTP 409, error_code ASOCIACION_DUPLICADA. - Reasignacion a otra area sin confirmar=true -> ConflictError, HTTP 409, error_code REASIGNACION_REQUIERE_CONFIRMACION (esto es lo que impone 'maximo una asociacion activa por sensor': la unica forma de tener una segunda asociacion es confirmar explicitamente que termina la anterior). La coleccion es autocontenida: registra sus propios dispositivos (A y B) y un sensor sobre el dispositivo A, reutiliza dos areas productivas activas ya existentes en TEST (finca_id=1) para el escenario 5, y reutiliza el area manualmente desactivada en BD para TC-M09-G56 (modulo9.infraestructuras id=12, 'Area Test Gap') para el escenario 3b - ver esa coleccion para el detalle de por que se preparo asi (POST /configuracion/infraestructuras esta roto, 500, no se puede crear+desactivar una nueva). Responsable: Juan Pablo. Prioridad: Alta. Tipo: Pruebas de integracion - Prueba de contrato de API (peticion/respuesta) sobre el backend desplegado en TEST. Herramienta: Newman. Nota: mismo patron de rechazo por reglas de integridad sobre la entidad 'asociacion', repetido en distintas condiciones.
