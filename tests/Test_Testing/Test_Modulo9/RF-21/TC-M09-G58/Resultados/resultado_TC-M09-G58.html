Collection: TC-M09-G58 (TC-M09-113) - Restriccion de rol para el registro de dispositivos IoT
Collection Description
TC-M09-G58 (RF-21, CU-05 Gestionar Dispositivos IoT), equivalente a TC-M09-113: verifica que POST /configuracion/dispositivos-iot solo pueda ejecutarlo un usuario cuyo rol tenga el permiso Crear (accion=1) sobre el recurso dispositivos_iot (id_recurso=11) en modulo1.permisos. Segun el docstring de dispositivo_iot_router.py: Admin y Ingeniero tienen C=1 (autorizados), Productor solo tiene R=2 (NO autorizado). NOTA: se intento inicialmente autoregistrar un usuario de prueba con rol Productor (mismo patron usado en TC-M01-084/TC-M09-G55..G57), pero POST /usuarios/ ahora exige un captcha_token real (RF-01, feature/rf01-captcha-registro recien mergeada a test) y el ambiente TEST tiene configurada la llave secreta real de Google reCAPTCHA, no la llave de pruebas oficial - un token arbitrario se rechaza con 400 CAPTCHA_INVALIDO, confirmado por prueba directa. Esto bloquea el autoregistro de usuarios de prueba para cualquier TC futuro que lo necesite, no solo este. Por eso esta coleccion usa una cuenta Productor ya activa que el usuario aporto (u20221206763@usco.edu.co, id_usuario=58, rol=2 confirmado por el claim 'rol' del JWT) en vez de crear una nueva. Resultado esperado: el intento del Productor debe rechazarse con HTTP 403 (error_code ACCESO_DENEGADO, ver src/shared/rbac.py::require_permission). Como control positivo, el mismo payload se reintenta con el token de Administrador para confirmar que el rechazo es especifico del rol, no un fallo general del endpoint. Responsable: Juan Pablo. Prioridad: Alta. Tipo: Pruebas de seguridad - Prueba de contrato de API (peticion/respuesta) sobre el backend desplegado en TEST. Herramienta: Newman. Nota: chequeo RBAC 201 (autorizado) vs 403 (no autorizado).
