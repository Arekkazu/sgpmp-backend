Collection: TC-M09-G56 - Validacion de datos al registrar un dispositivo IoT
Collection Description
TC-M09-G56 (RF-21, CU-05 Gestionar Dispositivos IoT) agrupa 4 escenarios de validacion/rechazo sobre POST /configuracion/dispositivos-iot, equivalentes a TC-M09-108, TC-M09-109, TC-M09-110 y TC-M09-111: 1. Serial vacio -> debe rechazarse (obligatorio). 2. Serial duplicado -> debe rechazarse (unico en el sistema). 3. Area invalida/inactiva -> debe rechazarse (inexistente e inactiva); incluye tambien el control positivo con area activa para confirmar que el rechazo es especifico de la condicion probada, no un fallo general. 4. Descripcion que excede el limite -> debe rechazarse; incluye el control positivo con descripcion exactamente en el limite de 100 caracteres. Contrato real verificado en el codigo (RegistrarDispositivoIotDTO y RegistrarDispositivoIotUseCase): - Los errores de validacion de Pydantic (serial vacio, descripcion > 100 caracteres) los traduce request_validation_error_handler en src/shared/error_handlers.py a HTTP 400 (no 422) con error_code VAL_ENTRADA y la lista fields - IMPORTANTE: este backend usa 400 para errores de DTO, distinto del 422 generico de FastAPI. - Serial duplicado -> ConflictError, HTTP 409, error_code SERIAL_DUPLICADO (campo serial). - Area inexistente -> NotFoundError, HTTP 404, error_code AREA_NO_ENCONTRADA. - Area inactiva -> BusinessRuleError, HTTP 422, error_code AREA_NO_DISPONIBLE. La coleccion usa un area activa ya existente en TEST (finca_id=1) para los casos que no prueban el area en si. BLOQUEO ENCONTRADO (2026-09-05): POST /configuracion/infraestructuras devuelve 500 ERROR_INTERNO con cualquier body valido - el fallo esta en AuditoriaInfraestructuraRepository.registrar() dentro de RegistrarInfraestructuraUseCase, que revienta con un error de integridad no mapeado por raise_from_db_error al insertar el registro de auditoria (registrar_infraestructura_use_case.py). Confirmado variando tipo_area, formato de superficie y con/sin descripcion - falla siempre igual, no es un problema de datos de entrada. Esto impide crear un area nueva para desactivarla y usarla en el escenario 3b (area inactiva), y en TEST no existia ninguna infraestructura inactiva de antes (se revisaron las 12 areas de las 7 fincas). El endpoint tampoco tiene forma de 'reactivar' un area por API una vez desactivada, asi que desactivar una real de forma permanente por este TC no era aceptable sin autorizacion. Por eso el escenario 3b depende de la variable de coleccion id_infraestructura_inactiva, que se completa a mano: alguien con acceso a la base de datos TEST pone es_activo=false en una fila descartable (ej. 'Area Test Gap', id_infraestructura=12, finca_id=6, que no tiene dispositivos asociados) y avisa el id para completar la variable antes de correr este escenario. El primer item de este bloque (precondicion) valida que esa area este realmente inactiva antes de intentar el registro, para no dar una falsa validacion contra un area que en realidad sigue activa. Responsable: Juan Pablo. Prioridad: Alta. Tipo: Pruebas de validacion - Prueba de contrato de API (peticion/respuesta) sobre el backend desplegado en TEST. Herramienta: Newman. Nota: variantes de rechazo sobre los campos de entrada del dispositivo.
